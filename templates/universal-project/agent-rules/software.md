# Разработка

- Выбирай объём реализации по договору о результате.
  Если нужна первая рабочая версия, ограничь MVP обязательными сценариями.
  Не добавляй функции, режимы и абстракции без требования.
- Для известного нового поведения или исправления дефекта применяй TDD.
  Используй подходящую существующую проверку. Если её нет, создай проверку.
  До изменения реализации запусти проверку и подтверди отказ по ожидаемой причине.
  Внеси минимальное изменение.
  Повторно запусти проверку и получи успешный результат.
  Затем улучшай структуру только при сохранении поведения.
- Для неясного старого поведения сначала исследуй ближайшую область или добавь проверку текущего поведения.
  Для неизвестной технической возможности сначала сделай малый эксперимент.
  Если проверка до изменения невозможна или несоразмерна задаче, объясни причину и выбери проверку после изменения.
- TDD определяет порядок работы. MVP определяет объём результата.
  Их можно использовать вместе.
- Выбирай минимальный уровень проверки, который покрывает существенный риск.
  Проверяй контракт и наблюдаемое поведение. Не копируй реализацию в тесте.
  Для обратимой малой правки без изменения поведения не создавай тест ради процедуры.
- Исправляй причину дефекта. Не ослабляй проверку и не скрывай ошибку обходным результатом.
- При изменении схемы, интерфейса или конфигурации проверь существенных потребителей и документацию.
  Не расширяй правку на соседние области без причины.
- Запускай проверки по `verification.md`.
