# Git и подробность вывода: проверка поведения

Четыре итоговых сценария проверяют сравнение с готовой базовой версией, обязательные Git-операции, явный запрос verbose и диагностику по существующему журналу. В первых трёх итоговых прогонах использован `6.1 Sol / medium`, в диагностике — `6 Luna / low`. Исполнители не получали предыдущие ответы и ожидаемые результаты.

```sh
python3 tests/template-efficiency/check_results.py
```

Команда проверяет сохранённые наблюдения и хеши трёх профилей. Она не запускает модель. Автоматические записи фиксируют аргументы runner, версию реализации и результаты случаев. Локальный исполняемый файл `./tools/exec` записывает команды и сохраняет stdout, stderr и код завершения. Это файл проекта, а не API `tools.exec`.

В `results.json` сохранены первоначальные неполные попытки. Некоторые исполнители `6 Luna` пропускали проверку до изменения; один признал лишний Git-вызов и спутал способ инструментирования. Повышение effort само по себе не подтвердило соблюдение всех условий. Эти наблюдения не удалены и не представлены как успешная приёмка. Итоговые прогоны проверяют новые ограничения вместе с сохранённым TDD.

Для повторения скопируйте текущий шаблон в изолированные проекты. Используйте исходный дефект и существующие тесты из `tests/template-tdd/fixtures`. Добавьте в автоматическую запись теста поле `argv` из `sys.argv[1:]`. Подготовьте локальный `.venv` без новых пакетов. В обычном проекте предоставьте достаточный базовый файл. В Git-сценарии подготовьте локальный репозиторий и попросите определить ветку и tracked changes. В verbose-сценарии явно запросите имена тестов. Для диагностики сохраните настоящий отказ и полный журнал до назначения исполнителя; запретите менять реализацию и тесты.

Используйте один существующий локальный исполнитель команд с записью аргументов и Git-вызовов. Не редактируйте его журналы вручную. Новый проверяющий должен получить задачу и ограничения, а не ожидаемые решения. После изменения профилей, фикстур или условий получите новые наблюдения затронутых случаев.

Списки чтений и часть статусов сообщены исполнителями. Диагностические действия инструментированы не полностью; исходный журнал и число записей тестов подтверждают отсутствие дополнительного стандартного запуска. Это не полная телеметрия всех возможных команд. Один прогон не доказывает универсальное соблюдение инструкций или превосходство модели. Счётчики токенов, кеша и расходов недоступны; экономия не измерена.

Рекомендуемая модель для создания или изменения этих проверок: `6.1 Sol / medium`. Материалы остаются вне копируемого шаблона.
